# Rules are objects too: a knowledge model for an active, object-oriented database system
<p subt>Dayal <em>et al.</em> (OODBS 1988), doi:10.5555/60295.60304</p>

## Abstract & Introduction

**ECA** 即 **Event-Condition-Action** 模型<span com>，它这样定义一个 rule object：**ON event IF condition DO action**</span>。

### Background

在 DB 中，
- **event** 可以是 **db operation**, **temporal events**, **abstract signals** from arbituary user processes, **complex events** constructed from these primitive ones；
- **condtions** 也就是 queries over the database；
- **actions** 即 programs。

一般的项目中，如果希望在满足特定 condition 时执行某个 action，可以通过持续监测条件来达到效果。然而 DBMS 是被动的。它们只有当被明确请求时才会执行操作，而如果让用户程序来 **poll (periodically query)** DB，频率高了容易造成 flooding。一个备选项是让每一个更新 DB 的应用来 check cond.，但是这又会破坏架构的内聚性。

为此，Active DBMS 试图通过定义一套规则，将 condition check 交给 DBMS。这使得很多其他功能也会因此变得更容易做。

## Method

### Requirements for Modelling Rules

#### Event types

对于报警功能，必须建模多种事件类型。被监控的条件可能很复杂，而且不仅可以定义在单个数据值或单个数据库状态上，还可以定义在**数据对象集合**（如员工工资总额超过部门预算）、**状态之间的转移**（例如目标的新位置比旧位置更近）以及**趋势和历史数据**上（例如传感器的输出在过去一小时内单调递增）。

#### Coupling

执行模型的需求可能因应用而异。一些规则需要是 **immediate** 的，立刻发生且阻塞原事务，直到规则被完全处理；如果规则导致其他事件级联触发，可能导致相当长的延迟。为了改善这一点，一些规则可以做成 **detached**，在单独的事务中运行，以改善响应时间和并发性。

如果发生了分离，那么**参数**可能会需要被**保护和传递**，以避免在不必要的情况下重新计算。如果 action 和 condition 被分离，那么 action 执行时可能需要**重新求值**，因为 DB 状态已经被更改。但无论它们是耦合还是分离，

无论耦合还是分离，一旦触发事件发生，它们往往需要在相对紧的时序之内发生。**如果动作被任意延迟地执行，就可能造成相当大的损失**。硬约束（精确时间）基本是很难在 DB 中实现的，可以考虑使用优先级或者值函数<span com>（建模代价）</span>来排序；如果时序约束无法被满足，考虑使用不那么新近或近似的数据、产生近似答案，以及完全放弃某些动作。

最后，常常需要一种机制来激活和停用单个规则或规则集合。这也有助于提供一种上下文机制，以限制必须被搜索的规则数量。在 scene A 下适用的很多业务规则会需要在 scene B 中被停用，因为它们是不同的上下文。

#### Integrity

对于完整性控制，ECA 规则比简单触发器提供更多灵活性。有些约束需要在更新事件发生后立即求值（例如值在范围内），其他约束需要被推迟到更新事件所在事务的末尾且通常有必要让其只触发一次。

此外在非传统环境如 CAD 中，可能需要**延迟约束求值**（例如在设计阶段结束时，而不是每个事务之后），**应显式用户请求进行约束求值**，以及在约束被违反时**指定依赖上下文的动作**（例如，导致违反物理规律的更新必须被禁止，但导致违反合同约束的更新可能只需要通知设计者并记录日志）。

#### Access

对于访问控制，它经常需要检测和记录 **beginning of an event**，这是十分有趣的。因此，数据库操作不能被当作一个瞬时的事件。此外，events of interest 除了数据库更新还包括 read。最后，动作必须是 **causally independent** 的：不能让攻击者获得**通过让事务回滚来抹掉访问痕迹**的能力。

#### Derived Data

关于派生数据，ECA 在其维护方面提供了灵活性：基数据更新时立即采取、按需采取，或在其他指定事件时采取。

### Rules as first class objects

此前关于主动 DBMS 能力的工作中提出的触发器和规则只满足上一节识别出的需求的一个子集。它们只提供非常有限的事件集合，经常不区分触发事件与条件，并且在事件、条件和动作之间只有单一耦合模式。

本文基于 HiPAC DBMS，在 HiPAC 的知识模型中，规则被当作一个对象来看待。规则有三个必需的特殊操作：**fire**，**enable** 和 **disable**。<span com>因此，规则也可以被查询、被组织、被继承、被事务保护、被版本管理。</span>

#### Advantages

把规则当作模型中的 first-class object 有一些优势。**第一，规则可以与其他对象相关联，也可以拥有属性**。由此可以通过上下文分组规则（例如所有具有某属性值的规则，或所有与某上下文对象相关联的规则），从而缩小规则搜索的范围。还可以创建规则对象类的子类，并在这些子类上定义特殊属性或操作。

**第二，它们可以像其他对象一样被创建、修改、删除和保护**；事务必须获得规则对象上的读锁才能触发它，必须获得写锁才能修改、删除或停用它。这使得正在被某事务触发的规则不能被另一个事务修改、删除或停用。

### Event

规则的事件函数产生一个事件实体，有 identifier 和形参列表，且定义 **signal** 操作。signal 操作把为事件指定的形参绑定到实参，也就是事件的“发生”。

**事件检测在数据流层面完成，不产生数据库访问开销，也不与事务的数据库操作产生耦合**。

#### Primitives

存在三类**原始事件**：**数据操作事件**，**clock time**，以及**外部通知**。由于 HiPAC 是面向对象的 DBMS，所有数据操纵都表示为对象（即 entity）上的函数。例如，`Insert_Position(Ship_ID: String, Location: (Lat, Long))` 把 `Position` 实体类型的一个实例插入数据库。为每个操作也可以定义 begin 和 end 两个时点。begin 发生在谓词求值完成之后，一组实例已经确定的时刻。

- 对于**系统提供的操作**，如更新和检索，可以预先定义操作执行期间发出开始和结束事件的点，以及与这些事件关联的参数。
- 对于**用户定义的操作**，事件及其参数必须由函数定义者指定。
- **事务的开始和结束**也被视为本模型中的事件。
- **时间事件**分三种：**绝对**、**相对**（参考事件发生后一段时间）、**周期**（含首次发生点）。
  - 与这些时间类型关联的有：度量时间的单位、时间的性质（离散 vs 连续，线性 vs 分支），以及谓词（after、before、equal）。

#### Acstract

**抽象事件**不一定与数据库操作或时间关联，也不能被 HiPAC 直接检测。这些事件及其参数在模型中定义，但由用户或其他程序检测并发出信号。抽象事件可以递归定义，在动作中再派生事件。

#### Compound

复合事件有三种构造方式：
- `(E1|E2)`，是一个 outer union；
- `E1;E2`，存在一个先后顺序；
- `E*`，类似一种 delayed event：如果在一个事务中出现了至少一次 `E`，事务结束时触发 `E*`。

最后一种的用处在于，integrity check 等不需要每次出现 update 时都检查，而只需要检查一遍最终的 accumulative result。<span com>←然而这不是 `E;event_end` 就能解决吗？</span>

复合事件规范构成正则表达式，因此可以被有限自动机检测。

### Structural Def.

定义规则的结构：
- **Rule identifier**，就像任何其他 entity 一样有一个 unique id
- **Event**，可以为其定义带类型的形参
- **Condition**，E-C coupling + 规则触发时要求值的一系列查询
- **Action**，C-A coupling + 具体操作
- **Timing constraints**，优先级/紧迫度或值函数
- **Contingency plans**，时序约束无法满足时要执行的替代动作
- **Attributes**，可以是标量值如字符串和整数，也可以是拥有属性的复杂实体

#### Condition

条件有四种 E-C coupling mode：
- 触发事件被发出信号时**立即 (Immediately)** 求值，此时触发事务的执行被挂起。
- **延迟 (Deferred)** 模式，此时条件在事务末尾、触发事务提交之前被求值。
- **分离但因果依赖 (Detached but causally dependent)**，此时条件在单独的事务中求值，但在触发事务提交之后；如果触发事务中止，条件不被求值。
- **分离且因果独立 (Detached and causally independent)**，此时条件在单独的事务中求值，调度器可以自由地独立于触发事务调度这个事务。

条件的第二个组成部分是一组查询，如果所有查询都返回非空答案，条件被认为是满足的。使用一组查询而不是一组真假条件背后的考虑是，**如果查询的答案非空，它们可以被添加到规则的触发实体中，并在动作执行时被作为额外参数传递**。动作部分于是可以引用事件时刻的绑定、条件求值时刻的绑定，以及动作执行时刻的数据库状态。

#### Action

同样四种 coupling mode：发出信号后立刻执行；延迟到发出信号的事件结束后执行；分离且因果依赖；分离且因果独立。

操作可以是数据操纵语言中的一个程序（数据库操作），也可以是发给外部程序或进程的消息；可以定义在规则触发实体中传递的参数之上，也可以使用操作执行时刻的数据库状态。

#### Timing constraints & Contingency plans

时序约束可以附加到 HiPAC 系统中的任何任务上，而不是规则独有的特性。

应急方案可以具有比单个规则的动作部分更全局的范围。例如，方案可以是放弃一些任务、事务或规则，或者在过载条件下处理一个不同的集合。
