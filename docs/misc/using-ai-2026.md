# Using AI in 2026

## 引入

我们常常产生一些需求，比如想要查询资料、想写代码，遇到一个希望得到解答的问题，etc. 为了解决这些需求，我们可能会求助于 AI 来解决它。

当我们“使用 AI”，我们使用的一般是 **AI 服务 (AI service)**。服务就是**一个实体对外提供能力**；在 AI 领域，一般来说服务的提供者或者说**提供商 (provider)** 就是 AI 公司。它们向用户供应 AI 产品。

AI service 在当下基本分为两类：**聊天服务 (chat service)** 和 **API 服务 (API service)**。

### 聊天服务

如果本文的读者曾经使用过诸如 ChatGPT (https://chatgpt.com) 或是 DeepSeek (https://chat.deepseek.com) 的网页和 App 端，应该会熟悉如下模式：

<div stmt>

**1\. Q-A Model.**
- 用户发送消息给 AI；
- AI 收到消息，生成回答。
</div>

这是**一轮对话**的过程，而为了让用户可以就着答案进一步追问，可能需要改进为：

<div stmt>

**1\.1. Q-A Model with Chat History.**
- <span key>维护一个**对话历史 (chat history)**</span>，初始为空；
- 用户发送消息时，实际上发生的是<span key>向对话历史的尾部**追加 (append)** 一条消息</span>；
- AI 收到对话历史后，向对话历史尾部追加一条回复；
- 用户可以查看完整的对话历史，其中包含了每一轮对话。
</div>

### API 服务

如果要评价使用 AI 的**范式 (paradigm)**，也就是“使用 AI 的基本思路”的话，把 AI 当成一个聊天机器人在很多时候是很低效的，有一些显而易见的问题。

首先，网页聊天必须要用户手动发送消息之后才能回复，如果用户有一个非常重大的多步骤的任务，需要在每一步人工介入，而不能给 AI 一个选题，让它“自己跑”直到完成或者卡住。

再比如，网页端提供的服务往往是非常有限的，很多网页端无法（以文件等形式）导出会话历史，手动一条一条复制归档的话就会很痛苦。

那么有没有一个替代的思路呢？那就是通过代码来调用 AI 服务，也就是 API Service 即 **Application Programming Interface 应用编程接口**。

#### 使用 API 模拟网页服务

用户人工输入一条消息并发送，本质上是往服务器发了一个数据包；那么显然也可能实现这样一个事情：允许比较高级的用户通过代码往服务器发送一些数据，用程序来调用 AI 服务，而不是手写消息在网页端发送来调用 AI 服务。

这听起来像是“通过代码**模拟浏览器访问**”——除了它跳过了“模拟浏览器”这一步。模拟浏览器是程序伪装成人，借用人的身份去操作产品，而 API 调用是<span key>特别制定一套规则，允许程序通过另一套**给程序专门提供的入口**（也就是 API）来使用 AI 服务</span>。

<div stmt>

**2\. Chatting with API.**
- 用户使用程序通过**特定的格式**，发送数据给服务器，这个数据应提供完整的对话历史，包括一条最新的用户消息；
- 服务器解析数据，从中提取到了完整的对话历史，并使用 AI 大模型生成回复，把回复发送给用户；
- 用户本地的程序把这条回复拼接到对话历史，供用户查看。
</div>

#### Beyond chat service

因为 AI 可以写各种各样的文本，代码当然也包含在内，所以 API 提供的可能性就是：通过一定的外部支持，可以让 AI 写代码来调用自己，自动代替“用户发消息”的过程，完成自动化的闭环：

<div stmt>

**3\. Looped API Call**
- API 允许程序直接调用 AI 服务
- → AI 服务返回 AI 大模型写的代码
- → 本地程序运行这段代码，通过 API 调用 AI 服务
- → AI 服务返回 AI 大模型写的代码
- → 如此循环直到满足停止条件，或者需要人工介入
</div>

### Harness

上面提到，

> *通过<span key>一定的外部支持</span>，可以让 AI 写代码来调用自己*

这个“外部支持”一般就是指 **Harness**。Harness 是一套围绕 AI 构建的工具。在使用 AI 的时候，我们可能有很多需求：

- 我们希望为模型规定一套工作方式，比如对于复杂任务，必须拆解出详细的**方案 (plan)**，呈现给用户等待审批/验收通过，然后再执行，而不是一收到复杂任务就立刻执行。
- 我们希望为模型提供一些它可以使用的工具。目前作为主要生产力的 LLM 大语言模型只能输出文本，而文本只是单纯的数据。我们希望它可以读取和写入本地文件，以及进行运行代码并查看代码运行的结果，如此等等复杂动作。

Harness 让这些成为了可能。比如，

- 一些 Harness 会提供一个 **plan mode**，当进入 plan mode 的时候，Harness 会偷偷告诉 AI：现在你处于 plan mode，不能写入任何文件！对于用户来说，他们可能只需要点击一个按钮，或者输入 `/plan` 等命令，而不需要手动地、完整地指定 AI 现在应该怎么做。

- 一些 Harness 会告诉 AI：如果以 ***某个特定格式*** 输出文本，这个文本就会被当成代码执行。当获取到 AI 的输出，Harness 会解析其中是否存在对应格式的文本，并作为代码执行。这些 Harness 往往也会读取代码运行的输出，并发送给 AI 以便它进行下一步行动。

- Harness 基本会实现多轮的循环：AI 可以先执行代码（包括执行读取文件的代码来读文件），观察结果后进行决策，完成一个<span key>**调用工具 → 观察结果 → 决定下一步**</span>的闭环控制。没有这个循环，模型只是一次性文本生成；如果有了这个循环，Harness 就可以支持 AI 完成一个复杂的、多轮次的任务，直到完成、失败或需要用户干预。

#### 安装 harness ≠ 本地部署

什么叫本地部署？本地部署就是指**使用本地硬件跑本地模型**。举个例子，
- DeepSeek v4.1 1017 的参数量为 671B。
- 如果你没有下载几百个 G 往上的巨大模型，并使用手头的硬件运行它，那么就不算本地部署了 DeepSeek v4.1 1017。

### Agent

**Agent** 是一个能够感知环境，采取行动以达成目标的系统。基本上可以认为：

<div center>

**Agent = Model + Harness**
</div>

模型本身并不足以成为 Agent；模型只是一个给定输入，根据概率模型进行大量计算来预测其输出的东西。但是借助 Harness 给予的能力，模型的输出具有了多种效果，读写文件、执行代码、搜索、调用自己的 API，如此等等，而且**可以进行多轮的循环决策和行动来完成复杂的目标**，而不是只能接受一次输入、完成一次输出。

当我们通过 Harness 调用 API 时，它的内部围绕我们提供的目标构建了一个自我反馈的循环，来推进它收到的任务。这时候，它可以被认为是一个 Agent。

Agent 服务于多种不同的任务，比如如果使用 AI 进行编程任务，它可以是一个 Coding Agent；如果搭建一个平台让 AI 进行自主科研，它可以是一个 Autonomous Research Agent；如此等等。

## 关于模型

### 关于训练和推理

所有模型都是被**训练 (train)** 出来的，在训练过程中模型的参数会不断变化；当模型上线，也就是 available for service 的时候，模型会被冻结，所有的参数都固定在最后训练好的时刻不变。此时模型仍然可以用被冻结的参数进行**推理 (inference)**，推理就是根据给定的输入预测输出，生成内容。

一般而言，训练的成本显著大于推理，可以简单认为训练因为要正确地改变参数，所以会需要额外计算和保存很多中间数据，导致成本会是推理的数倍。

训练的过程中，模型的状态不断改变，如果提取出一个特定时刻模型的状态，那么这个状态就被称为一个检查点 (checkpoint)。广义上，训练完之后我们希望得到的结果，就是模型的一个 final checkpoint；此时模型的参数处于它训练完成，用于部署的状态。

<div info>

checkpoint 是训练过程中的一个存档点。部署时我们取的是训练结束时的 final checkpoint，只保留模型参数；而如果还想继续训练，就需要保留优化器状态等完整工程数据的 checkpoint。
</div>

checkpoint 的优点就在于它可以被备份和启用，比如如果觉得一个模型训练到这个程度不够，可以从最后的 checkpoint 继续；如果训练过头了，可以采用更早的、更加合适的 checkpoint。

一些时候，模型训练可能还没有到表现趋于稳定的阶段，能力还有进一步提升的空间，但 AI 公司会出于各种考量发布一个中间的 checkpoint，用以展示他们训练的阶段性成果。

### 模型名称

调用 API 的时候，我们一般可以问服务器申请一个列表，得到 a list of available models，比如对于 DeepSeek，它提供的是 `deepseek-flash` 和 `deepseek-v4-pro` 两个模型。这个是 **model id**，API 需要使用与此一致的 id 来调用它们。

相比之下，模型名称则自由很多，而且和 model id 并不总是一一对应的。例如，DeepSeek 曾经把 `deepseek-v4-pro` 更换成当时认为全方面更优的 DeepSeek v4.1 Flash，但后来又换回了 DeepSeek v4 Pro。

更常见的情况是**路由 (routing)**：路由就是从多个可能的目的地中选择一个。读者可能听说过以下具体案例：

- AI 公司会对 AI 模型进行灰度测试，让老模型的 id 有概率路由到新模型，来观察用户体验，i.e. 是否感受到模型的能力出现了显著的增强。

- 用户在使用一些 AI 公司的服务时，它们会静默地（在用户完全不知情的情况下）把名义上更强的模型的 id 路由到一个显然更弱的模型，即所谓的“降智”。例如，OpenAI 总是会在新模型发布后，很快将其降智；Anthropic 在判定内容“敏感”时，其“安全机制”会将请求自动回退给更弱的模型处理，但误报率很高。

## 关于使用

### 成本计算

一个需要重视的事实是：因为 <span key>**chat history 的本质是把所有之前的轮次发送一遍**</span>，所以发送过去的数据量会数倍乃至千百倍于用户追加的那一条消息，从而产生额外的费用。

不过事实上，AI 对话的成本并不是这么运作的；100轮次的对话追加一条消息，费用未必会比新对话的一条消息高两个数量级。这是为什么？

#### cache

有一个东西叫**缓存 (cache)**：在计算机领域，缓存的意思就是把一个东西存起来以便重复使用。

举个例子，对于常见的个人电脑，一个数据如果存在机械硬盘里，可能需要数毫秒才能完成一次读取；存在内存里，延迟则可能是100纳秒级，但是 CPU 内部有额外的小型存储器叫做 L1 cache 和 L2 cache，这两个的延迟是个位数纳秒。

把数据从内存这种低速的存储设备读出一次后，就暂存在 cache 这样的高速的存储设备里，对于高频使用的数据，这样做可以避免打断高速运行的 CPU 运算去等待一个很慢的内存读取。

计算机领域的**时间局部性 (temporal locality)** 原理告诉我们：一个曾经使用过的数据，很有可能被再次使用。当一个数据被缓存时，它常常会被反复多次使用，而缓存加快了后续每一次的读取，从而让电脑的运行效率大幅增加。

#### cache in AI

而 AI 领域的 cache 就是，对话历史一般是仅追加的，那么前面的绝大部分内容都是完全一样的；对于 AI 来说，它需要大量的数学计算来“理解”对话历史，但是如果我们把计算出来的结果直接暂存，后续就不用进行昂贵的运算了。

DeepSeek 在 cache 方面运用了很多很大胆的技术，让 cache read，也就是读取已经缓存好的内容，变得非常高效和廉价。其他 AI 企业也往往对 cache read 有所开发。对于 DeepSeek API，反映到 1M token (M = million) 的定价上，就是 **cache read 只有读取新数据价格的 2%**（￥0.02 vs ￥1）。

但是这一计算成立的前提是<span key>**缓存命中 (cache hit)**</span>，什么叫缓存命中呢？就是说 <span key>**cache 结果是有效的**</span>。

#### 缓存失效？

显然我们可以发现有两个可能导致 cache 结果无效：

- 一个是用户改动了前面的对话历史，导致已经缓存好的内容出现了不一致；

- 另一个是，AI 公司没有义务为用户无限久地保留缓存结果，绝大部分 AI 提供商只保留数小时，ds的话大概是半天到一天，因为缓存是保存的数据，会占用他们的内存或者硬盘容量的。

考虑以下几种情况：

<div stmt>

A. 用户白天和 AI 进行了多轮交互，每一轮都命中缓存，达到 90%+ 的命中率，省下了很多费用。

B. 用户一周前和 AI 进行多轮交互，现在重新启用这个长对话；因为缓存失效了，今天的首轮对话缓存未命中，损失了一两块钱；抛开这点不谈，之后每一轮都命中缓存，还是能省下很多费用。

C. 用户以数个月的时间跨度，每隔几天启用同一个对话，聊不到几句就停，每次首轮缓存都未命中，造成了可观的损失。

D. 用户每次对话之后会总结对话内容为一个精简的省流版本，今天之后想要继续同一个话题，就开一个新对话把省流版喂给 AI，这有很多明确的和潜在的好处，当然也导致了一定的信息损失而且比较累。
</div>

A、B 和 D 都是可接受的实践，而 C 应该尽量避免。

### 上下文管理

#### 所见非所得

一般地，和 AI 的对话历史就是它的上下文。当然这里的对话历史是广义的；AI 进行的文件读写和其他工具调用也算在对话历史当中，而且**并不以用户所见的方式计算 token 消耗**。

<div info>

AI 读取和输出文本的形式是 token。token 不一定是一个单词或者一个字符。
对于英文，一个 token 可以是一个完整单词、一个词根、一个常见片段、一个标点，甚至一个空格加单词。
</div>

比如，用户可能看到 AI 读了一个文件 `a.txt`，这个文件的长度是800个英文字符，也许消耗 \~200 tokens。但实际上可能是这样的：

- AI 调用 `<|tool_call_begin|>{ "name": "read_file", "path": "C:/Documents/User123/2026/123/project1/docs/important/aaaaa/a.txt"}<|tool_call_end|>`，而不是 simply `read "a.txt"`；

- 同理，得到的结果也往往不是纯粹的文件内容，而是可能带有元数据修饰。比如上面的例子里，AI 可能得到了这样一个带有很多其他信息的返回结果：

  ```json
  {
    "path": "C:/Documents/User123/2026/123/project1/docs/important/aaaaa/a.txt",
    "size": 800,
    "encoding": "utf-8",
    "truncated": false,
    "content": "Here is the 800-character article..."
  }
  ```

对于长文件，Harness 还可能只回传前 N 行、末尾若干行、匹配片段，或者一份摘要。光是读文件就长度计算上已经存在很多不一致，**这些 Harness 层次的细节并不总是会对用户展示**。

#### 保持对话简短

一个指导性的原则是：<span key>**如果不是涉及超大段文本的工作，上下文大概在 200k token 左右或之前就可以考虑切对话**</span>；现在的大部分主流 AI 能达到 1M 也就是一百万上下文，所以大概在上下文使用量达到 20% 左右就可以停止。这不是一个强制的指标，视任务的复杂性和进度，可以弹性地提前或延后。

<div info>

此处和下文的百分比都以 1M 上下文计。
</div>

这个原则背后有一系列原因。

首先，大模型对于长上下文容易出现注意力丢失，如果上下文很长，那么现在所有的主流 AI 作为概率模型，它们概率公式的分母就会同步增大。目前的主流大模型基于注意力机制，**通过计算各个 token 之间的关联度，来在模型的上下文中寻找和模型此刻的需求最相关的信息**。如果上下文很长，每一部分上下文都参与对最终结果的贡献，那么分配给每个局部的注意力就会被摊薄。

大部分模型在 15%-50% 不等的时候就会出现表现下滑，而参数量小的模型尤其严重，DeepSeek v4 Flash 在 25% 左右会下降到可能需要采取干预措施的级别。

此外，积极开新对话意味着冗长的历史对话不复存在，这可能有助于省下很多 cache read tokens；尽管缓存读的价格看起来很低，但每一轮对话都会累积成本，对于长对话而言结合对话本身的长度，也可以累积到不可忽略的程度。

#### 保持对话简短是足够的

OpenAI 的 coding agent **Codex** 被设定为在阈值的 95% 左右就压缩上下文，压缩上下文的意思就是让AI根据当前的完整对话历史提供省流，再把省流发给一个新对话。这个阈值在很长一段时间内是 372k，而在2026年中期被静默削减到了 272k。

OpenAI 官方在 2026 年 2 月发布过一项长任务压力测试，约25小时不间断地运行 Codex，产出约3万行代码，而这个过程中的单步峰值上下文为 270k tokens。

关于这个阈值存在一些争论，但实践上来说它确实能够一定程度上证明，**大型的复杂任务的成功并不依赖于上下文窗口必须如何如何巨大，而在于系统（或者可能还有人）能有效管理当前需要活跃在窗口内的信息**。

从编码任务转向更普遍的日常、工作和研究需求，这个结论可能会变得有些 tricky。比如，一个朴素的做法是把一本几十万字乃至数百万字的书以尽可能少的次数喂给 AI 让它阅读。

但是：
- 前面提到过，AI 存在长上下文注意力问题，这也许并不是一个好实践。
- 如果需要从书中提取特定信息，有很多主动检索或者把超长文本进行逐步压缩的方法。

本质上，超长上下文在很多时候更像是一个**不准确的需求**。这一方面固然是现有模型的能力限制所致，如果大模型的注意力问题得到解决，它的地位将会得到提升；但另一方面如果我们拆解需求（如高保真性、对全局的理解和把握），一次性喂进尽可能多的文本确实会在一些指标上暴露出其固有的缺陷。
